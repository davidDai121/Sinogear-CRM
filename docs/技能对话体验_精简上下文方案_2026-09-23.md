# 精简 CRM 上下文方案（短版，未改代码）

目标：老板本轮要求在 prompt 里不再被 30k 资料淹没；不加按钮；资料一份不丢（只是本轮不发）；任务契约不再跟着普通改稿走。

> 状态（2026-09-23 晚更新）：**代码已实施，未经 CRM 端到端验收。** 老板批准继续、Claude 主做代码。短输入（234 字）也失败过，不能承诺缩小上下文就会好；方案只是把老板要求在输入里的占比提高，效果要实测。实施与方案的差异见文末“七、实际实施与方案的差异”；离线重放体量见 `skill-updates/evaluation-2026-09-23/compact-context/重放体量与保留核对.md`。

## 一、按"本轮有没有老板要求"分两层，CRM 已知，不用猜意图

"有老板要求"不等于简单改稿：可能是复杂报价、特批、改数量港口。所以 B 层不是"最近 20 条聊天"就完：本单相关的报价授权、旧承诺、单客例外、待老板事项必须仍在（从工作记忆抽，见第三节），只是不再发整本账本和事实库原文。

| | A 层：无老板要求的生成 / 续聊 | B 层：有老板要求（生成框指令、讨论框任何输入） |
|---|---|---|
| 批准知识（事实文件） | 全文 | 全文（事实不能省） |
| 事实库 Sales Fact Library | 只发来源不是当前模板的条目（现在七档价和付款与知识重复） | 不发 |
| 工作记忆 Saved Customer Work | 全量账本 | 只发"已确认条件"摘要：车型、版本、数量、目的港、已报价口径、本单特批与例外、我方已承诺未交付事项、待老板事项，每项一行；账本原文不发 |
| 聊天历史 | 最近 50 条 | 最近 20 条，最后一条客户消息完整；涉及报价时再加"已确认条件"里引用到的原句 |
| 销售规程 CORE | 全文 | 全文（2.6k） |
| 语言规则 | 全段（3.9k） | 一行：Reply language = X（判定仍在 CRM 里算，只发结论） |
| 跟进契约 | 注入，输出 crm_followup，CRM 保存 | 默认不注入，见第二节 |
| 老板要求 | 无 | 最前 + 最后各一次（现状） |
| 估算体量 | 约 35k（与现在接近） | 约 14k |

判定就是现有变量：`guidance.trim()` 非空或走讨论路径即 B 层。没有新按钮，没有意图推断。

## 二、任务契约的边界

- **注入的轮次**：A 层；以及 B 层里老板要求明确提到跟进/任务/安排/提醒/什么时候再联系的。
- **不注入的轮次**：B 层其余，即改稿、口述、翻译、讨论、缩短、换语言。这些轮 CRM 走现有 `preserveExisting=true` 路径：不产生 crm_followup，不保存，界面不显示"跟进安排"。
- **不会丢什么**：任务表原样；上一轮生成建的任务继续有效；A 层下一次生成会重新评估。
- **会失去什么**：改稿轮不再自动把任务改成"核对并发送本轮草稿"。这正是老板要的（本轮不动任务），也和 David 实测方向一致。
- **跟进连续性**：跟进证据账本只在注入轮发；B 层不发也不会污染，因为不产生决定。

## 三、"已确认条件"摘要怎么来
从现有 `SalesWorkMemory` 已结构化的字段抽：QuoteVersions 的最新一版（车型/数量/目的港/口径/总价）、HistoricalGuidance 里未撤回的老板确认、openCrmTasks 的标题。不新增存储，不改账本，只是渲染另一个短视图。老板本轮说的和摘要冲突时以本轮为准，摘要末尾一句说明即可。

## 四、不做的
- 不做口述自动检测、不做句数/关键词修正、不加"口述转述"按钮。
- 不改技能正文和 CORE 措辞。
- 不删事实库、账本、语言判定逻辑；只改各层发什么。

## 五、验收怎么算
- 同一口述（Jaycee 那句）在 B 层跑一次：看正文长度、费用口径、有没有加卖点。这一次只能说明"缩小上下文有没有帮助"，不证明方法通用；已知 234 字短输入也失败过。
- 一次带特批的报价改稿：正文和策略里本单特批、旧承诺仍在，不因上下文缩小而丢。
- 一次改稿（"改成一句英文"）：任务 before/after 相同，界面无跟进摘要。
- 一次 A 层生成：跟进块照常保存。
- 如果 B 层口述仍是介绍体，只能说明这次上下文精简未解决问题，不能据此确定模型或平台根因。下一项可验证的对照是明确区分“待转述原文”和“供参考的背景”；讨论、报价等请求仍按实际意图处理，不能全部强制当成翻译。

## 六、改动量
`GPTReplySection.tsx` 两条路径各加一个 `compact` 分支；`sales-work-memory.ts` 加一个 `renderConfirmedSummary`；`gpt-prompt.ts` 语言段加短渲染；`sales-facts.ts` 按 provenance 过滤。约 100 行，回归用现有测试加 3 个用例。等解冻。

Codex 复核后修正（2026-09-23 晚二）：
- 跟进契约判定原来含“复核”，“复核一下这句英文 / 报价草稿”会误注入；改为只认明确的跟进安排或任务变更：跟进、动词+任务（建 / 改 / 取消…任务）、提醒+时间或联系动作（三天后提醒我、提醒我联系他）、安排回访 / 联系、什么时候再联系、几天后再催、待办；英文 follow up、add/update/move/close … task、remind + 时间或 to contact、schedule、check back。“提醒我这句怎么写”“复核报价草稿”“跟他说有消息我再联系他”“催款口径怎么说”都不注入（测试已列）。
- 续聊 / 讨论续聊原来先 `messages.slice(-50)` 再取锚点，50 条之前的真实报价 / 承诺进不了 anchors；现在把完整消息交给构造函数，full 层构造函数自己取最近 50 不变，compact 层从完整历史取锚点 + 最近 20。单测覆盖第 60 条以前的承诺，集成测试确认面板把完整历史交给构造函数。

未解决、如实记：
- Raynier（真实报价客户）的 B 层仍 47k：报价 / 运费规程 14k 仍加载，触发原因是“目的港与最新报价输入不一致”（`Haina, República Dominicana confirmado por cliente.` vs `Rio Haina, Dominican Republic`）和“最新车型兴趣不在报价方案内”（`Chery Rely R08` vs `RELY R08 Diesel 2.3T 8AT 4WD Comfort`）。这是工作流路由的字符串匹配偏保守，本轮没改（改了就是再堆规则），验收时若报价客户的普通改稿仍慢，这是下一个可核的点。
