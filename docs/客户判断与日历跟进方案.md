# 客户判断与日历跟进：第一版实施方案

日期：2026-09-17

状态：基于当前源码、累计 28 个客户/群聊的可见 GPT 记录及另 2 位客户的 CRM 片段完成设计修订，尚未实现、迁移数据库或发布。延续老板“每次请 ChatGPT 回客户时顺手判断，CRM 到期提醒”的使用方式，复用现有任务日历。

2026-09-17跨任务整合：六类业务技能及分批实施见[销售技能协同方案](销售技能协同方案.md)。运费与报价先落地；客户判断/跟进沿用本文约束，并作为同一回复流程的内部工作。关税不作为日常报价的必查项；六类技能不意味着六次独立对话或每轮全部调用。本文仍是未实现方案。

## 0. 老板补充的核心约束：减少负担

老板明确不希望每聊两句就改状态/重排任务，更不希望每天出现上百个客户需要跟进。此前“每次判断产生计划并进入日历”的设计过于积极，本次修正如下，此节优先于任何宽泛的自动排期描述：

- **状态与排期分离**：可以保存新事实和评估，但“有下一步建议”不等于有日历任务；没有值得提醒的理由时，合法输出就是不提醒。
- **日历只放需要记住时间的事**：销售明确承诺、客户明确约定，以及有证据、有实质交易障碍的一次性进展复核。单纯“已报价”“两天没回”“资料不全”不能自动入日历。
- **今日推荐独立于日历，不设人数上限**：老板再次明确一天可能出现多位优质客户，全部符合条件的机会都应保留并排序；没有合格对象允许 0 位。通过证据与行动价值筛选，不用每日配额控制数量。推荐未执行不变逾期、不每天累计、不为了凑数推荐。
- **真实事项完整展示**：如真实约定和优质机会超过处理能力，显示实际数量和优先顺序，不能为了减少数字隐去客户或擅自改约。
- **同一轮聊天稳定处理**：普通补充、礼貌回应和重复生成只更新相关事实，不建立新任务或反复改日期。有新约定、明确拒绝、采购时间/预算变化、决定性障碍解除才调整计划；重要变化立即生效，不用固定等待一整天。
- **等待可以没有日期**：缺资料、等客户决定、成本暂不合适都可仅记录等待条件；不强制给每位客户安排“检查进展”。普通待回复仍走现有“我该回”，不额外复制为日历任务。
- **复核是一次性**：例如 Jhon 请求多给一两天，窗口过去后可提醒检查一次；没有反馈时不生成无限的两日循环。新的提醒需要新依据或人工安排。
- **手机缺数据不批量变成待办**：保存不确定性，仅在打开该客户或已有重要事项到期时提示核实。不能把全部缺记录客户都挪到“待核实”清单制造新负担。

样本核查见 `客户跟进样本核查_2026-09-17.md` 及 `客户跟进扩展核查_2026-09-17.md`。样本结论是当前可见信息下的建议，未写入生产客户状态或日历。

## 1. 用户实际看到什么

每次通过 CRM 生成客户回复，同时得到一张仅内部可见的“客户跟进”卡：

- 投入建议：重点推进 / 正常跟进 / 低频维护 / 暂停 / 信息不足。
- 购买时间与意向：单独记录，不与今天是否要办事混为一谈。
- 依据：最多三条具体聊天事实，区分客户原话、销售补充和 AI 推断。
- 当前障碍：预算、时间、信任、车源、运费、决策人或未知。
- 下一步：一个具体动作，注明由销售、客户还是供应方推进。
- 时间：具体日期、发送后间隔或等待条件；显示依据更新时间。
- 操作：修改判断、改期、暂停、已处理、补充手机进展。

例（假设）：客户已确认车型、数量和港口，下一步由我方核实运费并报价；若已承诺明天下午给报价，才按该承诺落日历。若只是问过车型、没有时间约定或实质复核依据，正常处理当前回复即可，未来日期留空。不能因为销售自己发了很多图片，判断客户购买意向高。

## 3. 判断与提醒的分工

ChatGPT 在用户实际使用时理解上下文、提出判断。CRM 持久化结果、按日期展示，不需要每天重新启动 ChatGPT 才能提醒。

首轮、续聊统一要求返回独立 `[CRM Follow-up]` JSON 段，排在客户回复及翻译之外。必须包含 `change_kind`（无实质变化/新事实/计划变化）和 `disposition`（不提醒/等待条件/可选推荐/日历事项），日历事项必须给出独立的时间与业务依据。调整原先“仅三段”的指令，避免格式冲突。讨论模式仅在请求客户评估/计划更新时返回该段；一般商量话术不隐式重排日历。

解析器必须先切开内部段，客户回复填入及发送前的清理也必须识别它。格式错误只影响计划保存，不阻塞正常回复；界面明确提示“回复已生成，跟进计划未保存”。不能宽松猜测错误 JSON 后自动写入任务。

不额外引入付费模型调用，沿用现有网页生成与回读通道。直接在 ChatGPT 网页手动聊、没有回到 CRM 抓取结果的内容，第一版不能假定已同步；提供明确“读取最新判断”入口，并核验会话确实属于该客户。

## 4. 建议的数据结构

新增 `contact_assessments` 保存判断历史，而不是覆盖原始事实。字段至少包括：

- `id / org_id / contact_id / created_by / created_at`。
- `request_id`：CRM 生成的唯一请求号，用于幂等；不得由模型决定目标客户或组织。
- `context_at / evidence_through / source_kind / source_chat_url`：判断基于哪次资料，最后可验证消息时间可为空；数据库没有消息不代表没聊过。
- `opportunity_ref / responsible_party / identity_integrity`：本次需求或项目、下一步负责方、身份与来源一致性；不把旧车型的预算或旧项目失败迁移到新需求。
- `effort / intent / purchase_window / blocker / confidence`：有限枚举及有长度限制的补充说明，保留 unknown。
- `evidence / missing_information / next_action / scheduling`：结构化证据、缺口、动作与时间依据。
- `review_state`：建议、接受、被用户纠正等；人工覆盖独立记录。

`tasks` 增加可空的来源与关联字段，旧手动任务继续有效：`source`、`assessment_id`、`plan_key`、`priority`、`reason`、`schedule_basis`、`user_override_at`。现有 `due_at/status` 继续驱动日历。

通过一个事务 RPC 保存判断并更新对应计划。组织成员权限、客户所属组织、关联任务所属客户必须在服务端校验；RLS 按现有组织模型执行。并发请求以资料版本校验，旧上下文的慢响应不能覆盖新计划。

同一次返回重试、重新打开卡片、从本地恢复旧回复都不能重复创建任务。不同客户的生成请求即使中途切换聊天也不能串写。保存从请求完成处理器调用，不依赖组件显示副作用重新写历史结果。

同一需求、同一待办事项只保留一条生效计划；不同订单或明确承诺的多件事可以有独立任务。跨联系人/群聊只有核实属于同一项目后才关联，共用事项并保留来源与沟通负责人，不能仅凭同车型/同国家自动合并。未建立项目关联时保留客户边界。更新只作用于明确关联的 AI 任务，不能按标题模糊匹配去修改手工任务。

## 5. 日期与完成规则

| 情形 | 保存及提醒行为 |
| --- | --- |
| 客户明确约下周二联系 | 按约定日期建任务，记录原话与时区依据 |
| 销售已承诺今天查运费 | 今天的承诺任务，优先于一般培育提醒 |
| GPT 刚写出“报价后两天跟进”的草稿 | 等待发送确认；生成、填入输入框都不能启动计时 |
| 已确认实际发出报价 | 只有此前存在有实质理由的条件复核计划才启动计时；报价本身不创建跟进。无法可靠自动匹配发送时使用“手机已发/已发送”补记 |
| 等车源、等客户发资料 | 默认仅保存等待条件；只有具有实际复核价值时才设一次“检查进展”日期；不能把条件未满足时的检查当成催客 |
| 到期但最近消息可能缺失 | 先显示“核实进展”，允许补充手机回复、已处理或改期 |
| 客户提前回复 | 条件性“无回复再跟”转待复核，不能盲目照旧催；新回复不自动证明运费/报价等承诺已履行 |
| 用户手动改期或暂停 | 锁定对应人工决定，AI 可给建议但不能静默覆盖 |
| 没有新证据，再次生成相同建议 | 保留原截止时间，不能每天自动往后顺延 |
| 逾期 | 一直留在逾期清单，直到完成、改期或明确取消 |

日期由 CRM 校验并统一存 UTC，保留源时区并按用户显示时区分组。客户时区不明、相对日期来源时间不明时，不臆造精确约定。明确约定优先于 AI 默认间隔。

“信息不足”和“低意向”必须分开；礼貌回复、消息数量、国籍、预算低于当前车源都不能单独作为垃圾客户依据。暂停/低频必须有可读理由，新证据出现可以调整。判断不自动覆盖人工的成交/失败状态，也不触发现有广告转化上报。

## 6. 日历与提醒界面

保留月历，在顶部加入“今天要处理”“已逾期”入口。默认行动清单同时包含今日和逾期的真实事项，点击日历日期仍可查看那一天。“今日推荐”单独呈现，不设人数上限，按实际行动价值排序且允许为空；“等待条件”保留在客户档案和可选筛选中，不计入待办数量，“待核实”不成为全量缺数据客户的催办池。

任务行显示客户、动作、到期日期、判断理由和资料更新时间。约定/承诺事项优先，再按逾期和跟进优先级排序；低意向不取消已经承诺的事情。日历格子显示客户名字及简短优先级标记，避免堆长分析。

任务入口常驻数字与“我的/全部”一致。页面加载、保存后、恢复可见、跨午夜及定期刷新更新数据；若接 Realtime，显式补 tasks 的 publication 配置，不能假设已有（0025 尚未加入 tasks）。计数用有索引的 count，列表按日期范围/分页读，不能扫描全部 messages。

第一版为 CRM 内提醒。电脑关闭后，任务仍在数据库，重新打开会显示逾期；手机推送属于后续独立通知渠道，不能承诺当前扩展关机仍会推送。

## 7. 实施顺序与验收

前置：核查并隔离身份混杂输入，避免销售话术错标成客户表达；分离活跃度与业务阶段写入。Fernando 样本已显示同一客户下多份不同身份表单。只修新增同步不会修复旧数据库与 GPT 上下文，旧线程恢复评估前需重建可靠上下文。历史补状态不能批量将旧承诺变成今天的逾期；需要核查当前未结事项。

1. 先接判断协议、解析和内部卡片，选 10–20 个熟悉客户做只读试判。样本覆盖：热聊无推进、明确购期、沉默但有具体需求、预算不匹配、手机补充、明确暂停。比对人工理由、日期和误判情况，不以模型自评作为验收。
2. 试判合格后接事务保存与 tasks，先在测试客户验证幂等、人工改期、等待发送、客户提前回复、旧结果晚到、保存失败及跨组织权限；真实 WhatsApp 操作按项目测试号规则执行。
3. 接日历、常驻计数和逾期清单，验证页面恢复/跨日、时区、团队范围与现有手动任务。
4. 小范围启用后检查提醒是否有用、是否重复、是否漏承诺，再决定扩大范围。上线需分别完成数据库迁移、构建、加载验证与发布，不能把本地完成等同已上线。

第一版成功标准：用 CRM 请 ChatGPT 帮忙后，销售能看到有证据的投入建议；仅有充分业务理由的定时事项进入原日历；真正逾期事项不会消失；普通推荐不产生逾期债务；补充手机进展能纠正判断；重试不重复、旧结果不覆盖新结果、手动决定不被悄悄更改、内部评估不会进入客户正文。额外用 100 位普通询价/礼貌回应样本验证不会机械生成 100 条跟进任务，0 个日历事项可以是正确结果。
