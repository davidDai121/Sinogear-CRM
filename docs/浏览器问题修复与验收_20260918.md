本轮是浏览器观察后的第一批关键修复。已完成相关代码、147 项回归、TypeScript 检查、Vite 构建，并重载本机扩展。尚未完成真实 GPT 报价到跟进保存的整条业务验收，不代表此前发现的所有问题已经解决。上述为修复结束时的状态；用户随后明确要求发布，发布结果见下方追加记录。

## 已确认的原因

1. WhatsApp 将部分消息渲染成 `data-virtualized="true"` 的空壳。旧读取器会把无正文空壳当成 `[媒体]`，导致本轮模型输入丢失真实文字或方向。数据库原有同步使用 ignoreDuplicates，不应描述成“覆盖了全部历史正文”：问题包括错误占位插入，以及重新看到真实正文后不修复旧记录。
2. 客户聊天正文中实际存在 Immersive Translate 的译文节点。只过滤 CRM 自己的翻译不足以保证输入是原话。
3. 立即跟进仍要求模型给出严格时间和来源组合，部分有效行动因时间格式或来源不匹配而无法保存。
4. 程序核算后的报价回到 CRM，ChatGPT 原回复仍显示占位符；这是展示链路不同，不能据此要求每次再调用 GPT 写一遍。

## 本轮改动

| 问题 | 处理方式 | 验证边界 |
| --- | --- | --- |
| 原话遗漏、混入译文 | 原文与翻译路径共享清洗逻辑；跳过虚拟空壳；显式生成前尝试加载最近挂载的 50 行；仍缺消息则明确报错 | 有离线虚拟滚动测试；本轮测试号消息很少，未完成长聊天真实压力验证 |
| 数据库保留旧错误占位 | 同步时等待重新观察到的正文、方向、缺失时间修复；比较旧值后更新，失败重试 | 不批量猜测修复未重新观察到的历史消息；不覆盖并发修改或原有来源 |
| 立即跟进保存失败 | `act` 的执行时间由程序给出，仍验证真实消息依据；未来复核保持严格日期验证 | 缺失机器段、非法未来复核等情况仍可能触发修复调用；人工安排保护保留 |
| 报价显示不一致 | 将公开核算结果绑定到精确会话及 assistant 消息，在本机 ChatGPT 页面展示已核算草稿；不再为纯数字替换补一轮 | 本地显示层，不修改 ChatGPT 服务器历史；其他设备不保证看到同一展示；未做本轮线上整链验证 |
| 草稿过时 | 生成时保存输入指纹；新消息、发送记录、同 ID 正文变化后提示草稿未包含变化 | 旧草稿无指纹时仍主要依靠生成时间提示；暂未覆盖仅数据库发生的新变化 |
| 模板切换后丢失 | 按组织和客户保存手动选择，提供恢复自动匹配 | 已在测试号切换“客户/AI 回复”验证，测试后恢复 Miles V2 自动匹配 |
| 当地时间不符 | 优先采用客户档案国家，再考虑电话区号 | 多时区国家仍使用现有近似映射；本次不是国家字段全面治理 |

| 场景 | 合格标准 |
| --- | --- |
| 已确认目的港后客户回答 Oui / Yes | 回复沿用可追溯的已确认港口，不把短答当成新问题，也不重复询问已明确条件 |
| 已有批准车价、有效运费和装载数量，要求 CIF | 一次正常生成拿到公开总价、每台价及费用范围；CRM 与本机 ChatGPT 核算展示一致；不会仅为了填金额再调用 GPT |
| 有依据需要现在推进 | 跟进成功保存且不重复建任务；人工改期后不被模型覆盖 |
| 手动指定 R08 后切换面板或客户再返回 | 原客户仍使用指定模板；其他客户不继承该选择；恢复自动后使用自动路由 |

| 多车、纯电或混动报价 | 保留当前批准价格，装柜与分摊正确，DG 与港杂不重复；既定 CIF 口径不被旧材料改写 |

这些是验收目标，不是全部已通过的结果。财务核算回归通过不代表本轮重新验证了实际运价来源和有效性。
